Multi-Model Routing

You own two machines and a dozen models. A harness that uses one of each is leaving most of the capability on the table.

~18 minutes Prerequisites: 9, 11 Mission · Glossary

Every lesson so far has asked "which model?" as if the answer had to be one. It does not. A harness controls the model selection on every single call, and the turns in an agent loop are wildly unequal in difficulty.

The one idea

Most turns in an agent session are mechanical — acknowledge a tool result, pick the obvious next step, summarise. A few are hard. Routing sends each to a model sized for it.

The gain is not marginal. A 4B at 18 tok/s versus a 32B at 13 tok/s is a modest speed difference; a 4B on the small machine versus a 30B-A3B on the big one is a capability difference you can spend selectively.

Everything routing needs is already exposed. The design question is when to switch, not whether you can.

Four routing patterns

1. Summariser split

The easiest win and the one Lesson 11 pointed at. Compaction summaries do not need your best model. Route session_before_compact to a small fast model and the compaction spike shrinks — you still pay the prefix invalidation, but not the round trip on a large model.

2. Escalation

Start every turn on the small model. Escalate to the large one when a signal fires: the small model asked for help, produced a malformed call twice, or the turn involves multi-file reasoning. Cheap by default, expensive on demand.

The catch: escalating mid-session means the large model has no KV cache for this conversation. The escalated turn pays full uncached prefill on the entire context — Lesson 2's penalty, again. Escalation is worth it for genuinely hard turns and ruinous if it fires every third turn.

3. Sub-agent delegation

A tool that spawns its own agent with its own model and its own context. The parent's context grows by only the sub-agent's result, not its whole working history — so a sub-agent that reads twenty files returns a summary and the parent never carries those tokens. This is the strongest pattern for context conservation, and it composes with parallel execution.

4. Machine split

You have a 64 GB machine and an 8 GB machine. Point pi at both as separate providers. The travel laptop becomes a summariser and classifier; the desktop runs the main loop. It also works in reverse — on the plane, the 8 GB machine runs the loop and there is no fallback, which is the scenario Lesson 5 sized.

The routing decision, priced

Turn typeRoute toWhy
Acknowledge a tool result, continueSmallNear-zero reasoning depth
Summarise for compactionSmallCompression, not judgement
Classify or route a requestSmallOne decision, constrained output
Choose among 15 toolsLargeReasoning curve — Lesson 6
Multi-file refactor planLargeLong chain, compounding errors
Recover from repeated failureLargeThe small model already demonstrated it cannot
The rule that keeps routing honest

Every switch costs a full uncached prefill on the target model. So route on stable boundaries — a whole sub-agent task, a whole compaction — rather than per turn. A router that flips models frequently spends more on cold prefills than it saves in decode. Routing is a coarse optimisation; treating it as a fine one inverts the benefit.

Worked example

A 40-turn session: 32 mechanical turns, 8 hard ones, 3 compactions.

StrategyMechanicalHardCompactionsQuality
All small (4B)FastFails someFastPoor
All large (30B-A3B)FineGoodWastefulGood
Per-turn routingFastGoodFastGood, but 8 cold prefills
Coarse routingLarge (cache warm)LargeSmallGood, 3 cold prefills

The counter-intuitive winner: keep the main loop on the large model to preserve its warm cache, and route only the off-path work — summarisation, sub-agents, classification — to the small one. Routing the main loop back and forth destroys the thing that makes the main loop cheap.

Which reframes the whole lesson. Routing is not about making cheap turns cheaper. It is about keeping expensive work off the main context.

Check yourself

Question 1

What does switching models mid-session cost?

A full uncached prefill. KV caches are per-model — the target has never seen this conversation, so the entire context is prefilled from scratch. This is why routing must happen on coarse boundaries rather than per turn.
Question 2

Which routing pattern conserves the parent's context best?

Sub-agents. The sub-agent's working history lives in its own context; the parent receives only the result. A sub-agent that reads twenty files adds a paragraph to the parent rather than twenty files' worth of tokens — directly attacking the KV growth from Lesson 3.
Question 3

Given a large and a small model, where should the main agent loop run?

Large, keeping its cache warm. The main loop is where prefix reuse pays off, so it should stay put. Route the off-path work — summarisation, sub-agents, classification — to the small model. Bouncing the main loop between models destroys the reuse that makes it cheap.
Question 4

What is routing actually optimising?

Keeping expensive work off the main context. The decode saving from a smaller model is real but modest; the win is that delegated work never enters the parent's context, so it never occupies KV cache or gets re-prefilled. Frame it that way and the design decisions follow.

Addendum · the 48 GB M4 Added 2026-09-05 — the lesson above stands as written; this is what a third machine changes.

This lesson assumed routing meant choosing between a small local model and something larger elsewhere. With a 48 GB M4 on the trip, two things change.

First, routing becomes available away from home. The M4 runs Ornith-1.5-35B-A3B at an estimated 103–205 tok/s depending on whether it is a Pro or a Max — so the "expensive" tier in every routing pattern here is now in your bag rather than on the far side of a network you may not have.

Second, a pattern this lesson could not offer before: the M4 serves the M1. Run llama-server on the M4 and point pi on the 8 GB machine at it over the local network — the same OpenAI-compatible endpoint you would configure in ~/.pi/agent/models.json for any other provider. The 8 GB machine keeps its 4 GB model for offline work and borrows a 35B when both laptops are on the same Wi-Fi. Neither machine has to compromise.

The trade is the one this lesson already priced: a network hop adds latency to every turn, and the KV cache lives on the server, so cache reuse now depends on one client not invalidating another's prefix. With a single user that is a non-issue. See Three Machines.
