Lesson 3 · Local LLM Hardware

The Cache Has a Price

Prefix cache reuse was free in compute. It is not free in memory — and the bill arrives exactly where your model budget already hurts.

~14 minutes Prerequisite: Lesson 2 Mission · Glossary · Cheat sheet

Lesson 2 ended on a win: keep the KV cache between turns and a quadratic session collapses to a linear one. Lesson 1's calculator quietly assumed that cache did not exist. Both cannot be true, and this lesson is where the two meet.

The one idea

The KV cache is memory you rent by the token. It grows linearly with context length, it lives in the same pool as the weights, and on a long-context agent workload it is not a rounding error — it is frequently a quarter of your entire budget.

Which means context length is a model selection constraint, not just a setting.

What the cache actually is

Attention needs the key and value vectors for every previous token. Recomputing them each step would be quadratic, so they are computed once and kept. That store is the KV cache, and its size is fully determined by the model's architecture:

bytes per token = 2 × layers × kv-heads × head-dim × bytes per element the leading 2 is for K and V · nothing here depends on parameter count

Note what is absent: parameter count. Two models of the same size can have wildly different cache appetites, and the model card will not tell you — you have to read config.json.

Grouped-query attention is why this is survivable

Llama 3.3 70B has 64 attention heads but only 8 key/value heads. Queries stay plentiful; keys and values are shared across groups. Since only KV heads appear in the formula, GQA cuts the cache by 8× against classic multi-head attention. Without it, the numbers below would put long-context local inference out of reach entirely.

The number that changes your buy decision

Predict before you look

Your 25-turn agent session from Lesson 2 reached ~42,000 tokens. On the M1 Max you were planning to run Llama 70B at Q4_K_M — 43.2 GB of weights against ~48 GB of usable memory. Add the cache. Does the session survive?

320 KB × 42,000 = 13.8 GB of cache. Plus 43.2 GB of weights = 57.0 GB, against 48 GB available.

It does not fit — by 9 GB. Raising the wired limit to ~56 GB still does not save it. The 70B model you have been pricing this whole time cannot hold a long agent conversation on a 64 GB Mac, at any quantization that keeps it worth running.

This is the failure that gets misdiagnosed as slowness. The model loads, short chats work fine, and then somewhere around turn fifteen the machine starts swapping and throughput falls off a cliff. Nothing is misconfigured; you simply budgeted for the weights and not the cache.

Three lessons converging

Qwen3-30B-A3B wins on every axis at once, and each axis came from a different lesson. Lesson 1: it is MoE, so only ~3.3B parameters are read per token — decode is an order of magnitude faster than any dense model here. Lesson 2: that speed is what a cache-reusing harness converts directly into turn latency. Lesson 3: just 4 KV heads means the smallest cache in the table.

You would never find this by shopping on parameter count. "30B" looks worse than "70B" on every spec sheet and model leaderboard, and is dramatically the better choice for your workload on your hardware.

A better model has since arrived that satisfies these same criteria harder: Ornith-1.5-35B-A3B — ~3B active, only 2 KV heads (80 KB per token against Qwen3-30B-A3B's 96), MIT licensed. The reasoning on this page is unchanged; the winner is. See Lesson 15.

The other lever: quantize the cache

The cache is just numbers, and it can be stored at reduced precision like the weights. In llama.cpp: --cache-type-k q8_0 --cache-type-v q8_0 halves it. Llama 70B's 13.8 GB becomes 6.9 GB, bringing the total to 50.1 GB — still over 48, but now within reach of a raised wired limit. Quality cost is small at Q8 and becomes real at Q4. Try it in the calculator above.

Where this lands in pi

pi handles context exhaustion with compaction — summarising older messages while keeping recent ones, automatically or via /compact. You can now see exactly what that does, and it cuts both ways:

CompactionEffect
Frees KV cache memoryGood — the whole problem in this lesson
Rewrites the conversation prefixBad — invalidates prefix cache reuse from that point
Next turn after compactionPays full uncached prefill on the new, shorter context

So compaction is a priced trade, not a free cleanup: you buy memory with one expensive turn. And because pi lets extensions implement custom compaction, this is a decision you can own rather than inherit. A compaction that fires at 90% of budget and cuts deeply costs one slow turn rarely. One that trims a little every few turns keeps memory flat and destroys your cache continuously. Same feature, opposite performance characteristics.

Worth building

The napkin work for a compaction plugin is now fully in your hands: cache bytes per token from this lesson, prefill rate from Lesson 2, decode rate from Lesson 1. That is enough to compute the optimal compaction threshold for a given model and machine, rather than guessing at it.

Check yourself

Question 1

How does KV cache size scale?

Linearly with context length. Every token contributes a fixed number of bytes, set by the architecture. Parameter count does not appear in the formula at all — which is why a 30B model can need less cache than an 8B one.
Question 2

Llama 70B Q4 is 43.2 GB of weights, plus a 13.8 GB cache at 42k context, on a machine with 48 GB usable. What is the outcome?

Over by 9 GB. 43.2 + 13.8 = 57.0 against 48. The 5 GB of apparent headroom you had when counting weights alone was an illusion created by ignoring the cache — and it evaporates at around 15k tokens of context.
Question 3

Grouped-query attention shrinks the KV cache by reducing which quantity?

Key/value head count. The distractor matters: GQA keeps all 64 query heads on Llama 70B and shares just 8 sets of keys and values between them. Query heads cost compute; only KV heads cost cache.
Question 4

pi's compaction summarises older messages to reclaim context. What does that cost?

Prefix cache validity. Rewriting the early conversation changes the prefix, so the cached keys and values no longer correspond to it. The following turn re-prefills from scratch. The effect is one expensive turn, not a permanent slowdown — which is precisely why compaction should be rare and deep rather than frequent and shallow.

The capacity picture is now complete

Three lessons, three costs, and you can price any model on any machine from published specs alone: weights from parameter count and quantization, cache from architecture and context, speed from bandwidth and active parameters. Everything the buy decision needs is assembled.

Which is exactly why the next lesson is hands-on measurement. Every number in this workspace is either sourced from someone else's benchmark or derived on a napkin.
