Lesson 10 · Local LLM Fluency

Tool Design for Local Models

Tool schemas written for a frontier model are a liability in front of a 4B. The fix is not better prompting — it is designing so that fewer decisions reach the model at all.

~18 minutes Prerequisites: 8, 9 Mission · Glossary
The one idea

Every tool you register is paid for twice: once in tokens, on every single prefill for the rest of the session, and once in decision load — every additional tool is another way for a weak model to choose wrong.

Frontier models absorb both costs invisibly. A local 4B does not.

The token bill

Tool definitions live in the system prompt region, injected by the chat template. They are part of the cached prefix, so with cache reuse you pay their prefill once — but you pay their KV cache footprint forever.

At 144 KB per token, a generous tool catalogue can consume the entire context budget of the 8 GB machine before the user says anything. On a 64 GB machine the same catalogue is a rounding error. Tool count is a hardware-dependent design decision, which is not how anyone normally thinks about it.

The decision bill

From Lesson 6: quantization damages multi-step reasoning first. Tool selection is multi-step reasoning — read the situation, compare candidates, pick, extract arguments. Errors compound:

P(correct turn) = P(right tool) × P(right args) × P(right stopping) four steps at 95% each is 81% end to end

Adding a sixteenth tool does not cost 1/16 of the accuracy — it costs more, because the new tool is usually similar to an existing one, and similar options are exactly what a degraded reasoner confuses.

Seven rules

1. Fewer tools, wider each

Prefer one file_edit with a mode parameter over replace_line, insert_after, delete_range and append_file. A constrained enum inside one schema is a decision the grammar can enforce; four separate tools is a decision only the model can make.

2. Make names semantically distant

search_files and find_in_files will be confused. grep and list_directory will not. Distance in meaning is the cheapest accuracy you can buy — it costs nothing at runtime.

3. Descriptions state when, not what

A weak model needs a selection cue more than an explanation. "Read a file from disk" describes the tool. "Use when you need the contents of a file you have not already read" tells the model when to pick it — and when not to.

4. Constrain every field you can

An enum makes wrong values unrepresentable via the grammar (Lesson 8). A free-form string makes them merely unlikely. Every field you can turn into an enum, a bounded integer, or a pattern is a failure mode deleted rather than discouraged.

5. Return the minimum that answers the question

From Lesson 9: tool results are next turn's prefill and permanent cache occupancy. Return the matching lines, not the file. Truncate with an explicit marker so the model knows more exists and can ask for it — a second cheap call beats one catastrophic one.

6. Validate in beforeToolCall, not in the prompt

"Always check the path exists first" in a system prompt is advisory, costs tokens on every turn, and degrades with quantization. The same rule in beforeToolCall is free, deterministic, and blocks the call with { block: true } before it costs anything.

7. Fail loudly, in the runtime's idiom

pi's convention is explicit: throw when a tool fails; do not return the error as content. The runtime turns the throw into a failed tool result the model can see and react to. An error returned as ordinary content looks like success to the model, which then builds on it.

The second column is not a worse harness. It is the same harness designed against a real constraint — and it will also be faster and cheaper on the 64 GB machine, because nothing about these rules is specific to being memory-starved.

The counter-intuitive part

The instinct when a small model misuses a tool is to explain more — longer descriptions, more examples, firmer instructions. That makes it worse: it enlarges the permanent prefix, consumes cache headroom, and adds context the model must reason over before it can act. The fix is almost always to remove a decision, not to explain it better.

Check yourself

Question 1

Registering 30 richly-described tools on the 8 GB machine costs what, primarily?

The entire cache headroom. ~12,000 tokens at 144 KB each is ~1.73 GB — the whole budget left after weights. Prefix caching makes them free in time and permanently expensive in memory, and memory is the binding constraint on that machine.
Question 2

A local model keeps picking the wrong one of four similar edit tools. Best fix?

Merge them into one tool with a mode enum. That converts a model decision into a grammar-enforceable one — the wrong value becomes unrepresentable. Longer descriptions and examples enlarge the permanent prefix and add reasoning load, making the problem worse.
Question 3

Which description helps a weak model most?

When to use it. The model's hard problem is selection among candidates, not comprehension of any one. A selection cue — "use when you need X and do not already have it" — targets the step that actually fails. Mechanism and return shape belong in the schema.
Question 4

In pi, a tool's handler hits an unreadable file. What should it do?

Throw. pi's documented convention — the runtime converts it into a failed tool result the model can see and react to. An error returned as ordinary content is indistinguishable from success, and the model will build on it. Empty content is worse still: it reads as "the file is empty."
