Lesson 2 · Local LLM Hardware

The Cost of a Turn

Lesson 1 modelled one long generation. An agent loop is the opposite: many short turns over a long, growing prefix. Different physics, different hardware answer.

~15 minutes Prerequisite: Lesson 1 Mission · Glossary · Cheat sheet

You are building harnesses for CLI agents. So the number that matters is not "tokens per second" in the abstract — it is how long a turn takes, from you hitting return to the agent finishing its move. That decomposes into two operations with completely different cost models, and Lesson 1 only taught you one of them.

The one idea

A turn is prefill (read the prompt) followed by decode (write the reply). Decode is bandwidth-bound, as you know. Prefill is compute-bound — a completely different bottleneck, on a completely different spec.

Which one dominates your agent loop is not a property of the hardware. It is a property of your harness.

The proof, from a natural experiment

The llama.cpp benchmark thread happens to contain a controlled experiment. The M1 Max and the M2 Max have identical memory bandwidth — 400 GB/s — but the M2 Max has 38 GPU cores to the M1 Max's 32, about 19% more compute. Same model, same quantization:

M1 Max400 GB/s32530.1 tok/s61.2 tok/s
M2 Max400 GB/s38671.3 tok/s66.0 tok/s
Change0%+19%+26.6%+7.8%
LLaMA 7B Q4_0. Source: llama.cpp Apple Silicon benchmark thread.

Add compute, hold bandwidth constant: prefill tracks the compute, decode barely moves. That is the whole argument in one table. The two phases are limited by different resources.

Why prefill escapes the bandwidth limit

In decode you process one token, so each weight is read from memory and used for a single multiply-add — a matrix–vector product. In prefill you process the entire prompt at once. Each weight is still read once, but now it is used against every token position in the prompt — a matrix–matrix product. Read the same bytes, do 512× the arithmetic.

arithmetic intensity = FLOPs performed ÷ bytes read decode: ~2 per weight · prefill: ~2 × prompt length per weight

Raise arithmetic intensity high enough and the memory system stops being the constraint — the compute units become it. That crossover is exactly what the M1/M2 Max table shows.

Treatment of arithmetic intensity: JAX scaling book, All About Transformer Inference; kipply, Transformer Inference Arithmetic.

What a turn actually costs

turn time = prompt tokens ÷ prefill rate + output tokens ÷ decode rate the first term is your time to first token

Look at the ratio column, not the absolute numbers. The Mac is a balanced machine: prefill is only ~7–9× decode. The Spark is a wildly lopsided one: it ingests text 300–400× faster than it writes it. These are different tools, and which is better depends entirely on the ratio of reading to writing in your workload.

The agent loop's specific problem

Here is what makes agent harnesses different from chat. Each turn appends to the conversation: your instruction, the model's reply, and — usually the biggest chunk — tool output. The context only grows. And on a naive harness, every turn re-prefills the entire conversation from scratch.

Predict before you look

A 25-turn agent session. Starts at 12k tokens of system prompt and repo context, and each turn adds ~1,250 tokens. By the last turn the context is ~42k. On the M1 Max running 70B at ~53 tok/s prefill — how long is the wait before the last turn produces its first token?

42,000 ÷ 53 = 13 minutes. Before a single token appears. And you pay a version of that on every turn, growing each time.

Total prefill work across the session scales with the square of the turn count. This is the failure mode that makes people conclude local models "can't do agents" — and it is a harness bug, not a hardware limit.

The fix: prefix cache reuse

The conversation prefix does not change between turns — you only append to the end. So the KV cache computed for those tokens is still valid. A harness that keeps it around prefills only the newly appended tokens, and the quadratic blow-up collapses to linear.

Naive — re-prefill everything42,00013 min
Prefix cache reused1,25024 s

Same hardware, same model, ~33× difference. This is the single highest-leverage thing in a local agent harness, and it lives entirely on your side of the API.

Run the session yourself

Set a machine, set your context shape, then toggle the cache. Watch the bar chart change shape — that shape is the difference between a harness that works and one that doesn't.

Now the buy decision gets interesting

Take the same 25-turn session and run it on both machines, both with cache reuse on. Per turn: 1,250 tokens in, 350 tokens out.

Machine (70B)Prefill 1,250Decode 350Turn total
M1 Max23.6 s47.3 s71 s
DGX Spark1.6 s129.6 s131 s
The result that matters for your mission

Without cache reuse, the Spark wins an agent workload comfortably. Its 15× prefill advantage is exactly what a re-prefill-everything harness needs.

With cache reuse, the Mac wins again — because once prefill is small, decode dominates the turn, and decode is bandwidth, and bandwidth is Lesson 1.

So the hardware answer is downstream of a software decision you control. Build the cache-reusing harness and the cheap machine is the right buy. That is not a conclusion you could have reached from either lesson alone.

The caveat that will bite you

Cache reuse only works while the prefix is byte-identical. Trimming old turns to save context, injecting a timestamp into the system prompt, reordering tool definitions — each invalidates the cache from that point forward, and that turn costs the uncached price. Harness design decisions that look free are not.

Check yourself

Question 1

Two chips, identical memory bandwidth, one has 19% more GPU cores. Prefill rose 26%, decode rose 8%. What does this establish?

Prefill is compute-bound. The only variable that changed was compute, and only prefill responded to it. Decode stayed flat because its constraint — bandwidth — was held constant. This is why the two phases must be reasoned about with separate models.
Question 2

Your agent's context is 30k tokens and prefill runs at 50 tok/s. With no cache reuse, what is the time to first token?

10 minutes. 30,000 ÷ 50 = 600 seconds. Every turn. This is what "local models are too slow for agents" almost always turns out to mean — and it is fixable in software.
Question 3

With prefix cache reuse working correctly, what sets a mid-session turn's prefill cost?

Newly appended tokens. The cached prefix is skipped entirely, so cost tracks what you added this turn — mostly tool output. Which means controlling tool output size is a performance lever in your harness, equal in weight to any hardware choice.
Question 4

A harness that re-prefills the whole conversation each turn: how does total session cost grow with turn count?

Quadratically. Turn n prefills roughly n × tokens-per-turn, and summing over turns gives an n² term. With cache reuse each turn prefills a constant amount, so the session becomes linear. Same hardware, different asymptotics.

What this still does not cover

  • The KV cache costs memory. Reuse is free in compute but not in RAM, and at 42k tokens it is a serious fraction of your budget. That memory competes with the weights — which means it can force you off a model entirely. Lesson 3 prices it, and the answer disqualifies the 70B model this lesson just used as its example.
  • Batching. Since you are the sole user, this only matters for parallel subagents — but on a bandwidth-bound machine it is close to free. The Spark went from 20.5 to 368 tok/s of decode throughput at batch 32 while prefill stayed flat. If your harness fans out, that changes the maths again.
  • Whether the model can do the job at all. Tool-calling reliability and structured output are model-capability questions that no amount of bandwidth fixes. That is the other half of your mission and the workspace has not touched it yet.
