Lesson 1 · Local LLM Hardware

The Bandwidth Rule

One division problem predicts how fast any model will run on any machine. Learn it and most of the hardware market sorts itself out in your head.

~12 minutes Prerequisite: none Mission · Glossary · Cheat sheet

You already know that a $1,000 M1 Max beat a $4,699 DGX Spark on Llama 70B. That result looks like a fluke until you know the rule underneath it — and then it looks inevitable. This lesson teaches the rule.

The one idea

To generate one token, the machine must read every active weight in the model out of memory — and do only about two arithmetic operations per weight it reads. Almost no maths, an enormous amount of data movement.

So the speed of token generation is not set by how fast the chip computes. It is set by how fast the chip can pull bytes out of memory.

Every modern accelerator has vastly more compute than memory bandwidth. A matrix–vector multiply does one multiply-add — 2 FLOPs — per matrix element read. The arithmetic finishes long before the next bytes arrive, and the compute units sit idle waiting. This is what people mean when they call decoding memory-bandwidth bound.

Source: Arseny Kapoulkine, LLM inference speed of light (2024).

The formula

tokens/sec = memory bandwidth (GB/s) ÷ bytes read per token (GB) the ceiling — no implementation beats this

And the bytes read per token is just the size of the weights you have to touch:

bytes per token (GB) = active parameters (billions) × bits per weight ÷ 8 for a dense model, active parameters = all of them

That is the whole model. Two divisions and a multiply. Everything else in this lesson is a consequence of it.

Worked example: the machine you were quoted

MacBook Pro M1 Max, 64 GB, 400 GB/s of memory bandwidth. Run Llama 3.3 70B at Q4_K_M — roughly 4.9 bits per weight once quantization metadata is counted, so about 43 GB of weights.

400 GB/s ÷ 43 GB = 9.3 tokens/sec theoretical ceiling

Real implementations do not hit the ceiling. llama.cpp typically achieves 58–82% of peak bandwidth depending on the quantization and the backend. At ~80%, that predicts ~7.5 tok/s — and community measurements on M1 Max 70B Q4 land in the 7–9 tok/s range. The napkin got it right.

Efficiency figures: zeux.io. Measurements: llama.cpp Apple Silicon benchmark thread.
Predict before you look

Now the DGX Spark: 273 GB/s, running the same 70B model but at FP8 — 8 bits per weight, so 70.6 GB of weights. Do the division in your head. What is the ceiling, and what would you expect measured?

273 ÷ 70.6 = 3.9 tok/s ceiling. At ~70% efficiency: ~2.7 tok/s.

LMSYS measured the DGX Spark at exactly 2.7 tok/s decode on Llama 70B FP8. You just predicted a $4,699 machine's performance with one division.

Source: LMSYS, NVIDIA DGX Spark In-Depth Review.

Try it on anything

Change the machine, the model, the quantization. Watch which lever actually moves the number — that intuition is the point of the widget, more than any single result it prints.

Three consequences worth internalising

1. Quantization is a speed feature, not just a memory feature

Everyone learns quantization as "make the model fit." But look at the formula: bits per weight is in the numerator of bytes-per-token. Halving the bits halves the bytes read, which doubles the token rate. Going from F16 to Q4_K_M is roughly a 3.3× speedup, not merely a 3.3× size reduction. Try it in the calculator above.

Naming: in Q4_K_M, the Q4 is 4-bit, the K is the k-quant block scheme, and M is the medium-quality variant of it. Because k-quants store per-block scales alongside the weights, the effective bits per weight is non-integer — about 4.5–4.9 depending on the model's vocabulary size. Official quant list →

2. Mixture-of-Experts breaks the rule in your favour

An MoE model routes each token through a small subset of its parameters. Only those get read. gpt-oss-120b has 116.8B total parameters but 5.1B active per token — so it occupies ~62 GB of memory but only reads ~2.7 GB per token. That is why a 120B model runs an order of magnitude faster than a 70B one on the same box.

Restate the formula precisely: capacity is set by total parameters, speed is set by active parameters. Confusing the two is the single most common error in local-LLM discussion.

Honest caveat: MoE achieves a lower fraction of peak bandwidth than dense models, because the active experts are scattered through memory rather than read in one sweep. The formula still gives the right ceiling; just expect a worse efficiency factor.

3. More memory does not mean more speed

These are two independent specifications and the market constantly conflates them. The Spark has 2.7× the usable memory of the M1 Max and 0.68× the bandwidth. It can hold models the Mac cannot load at all, and it will generate tokens slower on every model both can hold.

Check yourself

Answer from memory before scrolling back. Getting one wrong here is more useful than re-reading the lesson.

Question 1

You switch a model from 8-bit to 4-bit quantization. What happens to decode speed?

Roughly doubles. Bits per weight sits in the numerator of bytes-per-token. Half the bits means half the bytes read per token, so twice the tokens per second — for the same bandwidth. The memory saving is the well-known half; the speed-up is the half people forget.
Question 2

Machine A: 128 GB memory, 273 GB/s. Machine B: 64 GB memory, 400 GB/s. Which generates tokens faster on a 40 GB model?

Machine B. Both hold the model, so capacity is irrelevant and only bandwidth decides: 400 ÷ 40 = 10 tok/s versus 273 ÷ 40 = 6.8 tok/s. This is the M1 Max versus DGX Spark result in the abstract — and the reason the cheap machine won.
Question 3

gpt-oss-120b has 116.8B total parameters and 5.1B active per token. Which figure sets decode speed?

The active subset. Only the routed experts are read per token, so 5.1B sets the speed. The full 116.8B still has to live in memory, so it sets the capacity requirement. Capacity from total, speed from active — keep them apart.
Question 4

A 24 GB model on a 960 GB/s GPU. What is the theoretical ceiling?

40 tok/s. 960 ÷ 24 = 40. Expect roughly 25–33 measured, once you apply a 60–80% efficiency factor. If you measured 8 tok/s on this setup, something is wrong — the model has probably spilled out of VRAM into system memory.

What this rule does not explain

Deliberately, the lesson modelled one thing: weights, one token at a time. Three gaps remain, and each is a later lesson.

  • Prefill. Reading your prompt is a different regime entirely — compute-bound, not bandwidth-bound. It is why the Spark does 803 tok/s of prefill on the same model where it decodes at 2.7, and why "slow" and "fast" swap places for long-context work.
  • The KV cache. Context is not free; it consumes memory and adds bandwidth traffic that grows with sequence length. Your headroom is smaller than the calculator suggests.
  • Batching. Serving many requests at once reads the weights once for the whole batch, which flips decoding from bandwidth-bound to compute-bound. This is the single most important fact for your batch-pipeline workload, and it changes the hardware answer.
