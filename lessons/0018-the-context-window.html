Lesson 18 · Local LLM Fluency

The Context Window

Lesson 11 taught you when to throw context away. This is the lesson about what was in there to begin with — and about the second ceiling, the one that is nowhere on the spec sheet and binds long before the memory runs out.

~22 minutes Prerequisites: Lesson 17, Lesson 11 Mission · Glossary · Cheat sheet
The one idea

A context window has two ceilings, and they are different numbers.

Memory says how much fits — weights plus KV cache against your budget, the arithmetic from Lesson 3. Attention says how much works — the point past which the model is still answering but is measurably less reliable.

On your 8 GB machine memory binds first. On the 64 GB machine attention binds first, by a factor of ten. Knowing which one you are up against decides whether the fix is compaction or curation.

What is in there before you say anything

The window does not start empty. A modest harness — seven tools, a system prompt, a project instructions file — has already spent a substantial fraction of the budget by the time the first user message arrives. Measured with Qwen3's tokenizer:

Measured against Qwen/Qwen3-1.7B. The tool schemas are seven realistic definitions — read, write, edit, bash, grep, glob, todo — averaging 92 tokens each (range 69–111). The project instructions file is this workspace's own MISSION.md, at 228 tokens per KB of markdown.

Two things in that table are worth sitting with. First, on the 8 GB machine's ~11,800-token memory ceiling, 1,706 tokens is 14% of everything you have, gone before the conversation starts. Second, the project instructions file is bigger than all seven tool schemas combined — and it is the item people never think to count.

Tools are not free, and not only in tokens. At ~92 tokens each, twenty tools is 1,840 tokens of pure schema. But Anthropic's guidance names the sharper cost: "one of the most common failure modes we see is bloated tool sets that cover too much functionality or lead to ambiguous decision points", with the test being — "if a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." That is Lesson 10's decision bill, restated by the people who ship it. Effective context engineering for AI agents, Anthropic Engineering.

The ordering rule

Composition is half the story; order is the other half, and it is worth more than it looks. Lesson 2 established that cache reuse survives only while the prefix is byte-identical. That single fact dictates the layout of the entire window:

arrange the context system prompt → tool schemas → project instructions → retrieved files → conversation → latest turn
most stable ────────────────────────────────▶ most volatile

Everything before the first byte that changes is reusable; everything after it is re-prefilled. Put a timestamp in the system prompt and you have moved the change to position zero, invalidating the entire cache on every single turn. Sort your tool schemas non-deterministically and you have done the same thing, silently, in a way that will never show up as an error.

Three rules that follow

1. Never put anything volatile early. No clocks, no random ids, no "files changed since last turn" in the system prompt. If the model needs the time, give it a tool.

2. Fix the order of anything iterated. Tool schemas, file lists, environment keys — sort them deterministically, or a map iteration order will cost you every cache hit.

3. Append; do not rewrite. This is why Lesson 11 insists on compacting the conversation body and leaving the stable head byte-identical.

See your own budget

Usable is not advertised

Now the second ceiling. A model card says 128k, or 262k. That number describes what the model will accept, not the range over which it stays reliable — and the gap is large, consistent, and well documented.

18 models, Chroma, 2025		 "Large Language Models (LLMs) are typically presumed to process context uniformly — that is, the model should handle the 10,000th token just as reliably as the 100th. However, in practice, this assumption does not hold."
The finding that should unsettle you. Chroma reports that "models perform better on shuffled haystacks than on logically structured ones" — coherent, well-organised text degraded retrieval accuracy relative to the same sentences in random order. And "even a single distractor reduces performance relative to the baseline, and adding four distractors compounds this degradation further." Neither result is something you would predict from the intuition that a model simply "reads" its context. Both mean an agent transcript — long, coherent, and full of near-miss content from earlier attempts — is close to the worst-case shape.

The mechanism is not mysterious. Attention compares every token to every other token, so n tokens create n² pairwise relationships. Anthropic's framing is that models have an "attention budget" they draw down as context grows; NoLiMa's authors attribute their measured declines to "the increased difficulty the attention mechanism faces in longer contexts when literal matches are absent." Same phenomenon, two vocabularies.

Why this changes what you build

On the 8 GB machine the constraint is physical. You run out of memory before the model runs out of competence, the failure is loud (swapping, Lesson 5), and the fix is Lesson 11's compaction trigger.

On the 64 GB machine the constraint is cognitive. You could hold 328,000 tokens and the machine would never complain — the model would just get quietly worse from about 32,000 onward. There is no error, no slowdown, and no signal. The fix is not compaction for memory, it is curation for quality: fewer tools, shorter tool results, and summarising a transcript long before anything is technically full.

Same harness, same code, opposite failure mode. A compaction plugin that only watches memory is correct on one of your two machines.

What to actually do

Anthropic names three tactics for long-horizon agents, and you have already built two of them:

TacticIn this workspace
Compaction — summarise and reinitialise as the window fillsLesson 11, with the trigger arithmetic. Add a quality trigger alongside the memory one.
Structured note-taking — persist state outside the windowNot yet built. A pi tool that writes findings to a file and reads them back on demand converts permanent context cost into on-demand cost.
Sub-agents — a focused context that returns only a summaryLesson 13. The context argument is as strong as the batching one: the sub-agent's working history never enters the parent's window.

Underneath all three is one principle, which is the sentence to keep: find "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." Every lesson in Part Three is a special case of it.

Check yourself

Question 1

Why must volatile content go late in the context, never early?

Cache reuse ends at the first changed byte. Everything after it is re-prefilled. A timestamp in the system prompt moves that break to position zero and costs you the entire prefix on every turn — with no error and no warning, only a session that feels slow.
Question 2

On the 64 GB machine, which limit do you actually hit first?

Attention, by more than tenfold. The memory arithmetic permits ~328,000 tokens; the evidence says reliability falls away around 32,000. Nothing reports this. The session keeps running and the answers keep coming — they are just worse.
Question 3

In the measured static prefix, which single item was largest?

The project instructions file — 863 tokens against 651 for all seven tool schemas, 128 for the system prompt and 64 for the environment block. Markdown runs about 228 tokens per KB, so an AGENTS.md that grows to 20 KB quietly costs 4,500 tokens on every turn.
Question 4

Chroma found models did better on shuffled haystacks than coherent ones. So?

An agent transcript is close to the worst case. It is long, coherent, and full of near-miss content from earlier attempts — exactly the distractors the same study showed compound degradation. It is not an argument for shuffling anything; it is an argument for keeping failed attempts and superseded tool output out of the window.
Question 5

A compaction plugin triggering only on memory pressure is wrong where?

On the 64 GB machine. There, memory permits ten times more context than the model handles well, so a memory-triggered policy never fires and quality degrades with no signal at all. The same plugin is correct on the 8 GB machine, where memory genuinely binds first.

This makes the Lesson 11 defect worse, not better. A compaction policy that triggers on memory pressure is now wrong on two of your three machines — and the M4 is the one you will actually work on during the trip. On it, memory permits five times more context than the model handles well, so the trigger never fires and quality decays with no signal at all.

There is a trap specific to having more memory: the 8 GB machine forced good hygiene. Short tool results, few files in context, aggressive compaction — all were survival, not discipline. On 36 GB nothing stops you reading forty files into the window, and nothing will tell you that you have. The failure mode changed from loud to silent, which means the policy has to become deliberate.
