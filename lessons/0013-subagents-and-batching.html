Sub-agents and Batching

Two ways to beat the bandwidth rule. Both work by the same trick — reading the weights once and getting more than one token out of it.

~20 minutes Prerequisites: 1, 4 Mission · Glossary

Lesson 1 said decode is bandwidth-bound and you cannot beat the ceiling. That was true for one sequence, one token at a time. Relax either constraint and the ceiling moves — a lot.

The one idea

The bandwidth rule says one weight read yields one token. Both techniques here break that ratio: batching gets one token for each of N sequences per read; speculative decoding gets several tokens for one sequence per read.

In roofline terms (Lesson 4), both move you rightward toward the ridge, into territory where the compute you already paid for finally gets used.

Batching

Process N sequences in one forward pass and the weights are read once for all of them. Matrix–vector becomes matrix–matrix, exactly as in prefill. The measured effect on a DGX Spark:

Llama 3.1 8B FP8PrefillDecode
Batch 17,991 t/s20.5 t/s
Batch 327,949 t/s368 t/s
Change−0.5%18×
Source: LMSYS DGX Spark review, SGLang.

Read that carefully. Prefill did not move — it was already compute-bound, so there was no idle capacity to reclaim. Decode went up eighteenfold, because it had been wasting almost all of it. The more bandwidth-starved a machine is, the more batching gives back.

What batching does not do

Per-sequence latency stays roughly the same, or gets slightly worse. Batch 32 delivers 368 tok/s in aggregate — about 11.5 tok/s each, versus 20.5 alone. If you are waiting on one answer, batching does not help you. It helps when you have several answers to wait on at once, which for a sole user means exactly one thing: parallel sub-agents.

Why this matters for your harness

From Lesson 9, pi's executionMode defaults to "parallel" — preflight sequentially, execute concurrently. If your tools are sub-agents, concurrency at the tool layer becomes batching at the inference layer, and four sub-agents cost far less than four times one.

Sub-agents in flightPer-agent decodeWall clock vs sequential
1baseline1.0×
4~70% of baseline~0.36×
8~50% of baseline~0.25×
Illustrative, extrapolated from the batch-1 to batch-32 scaling above; exact numbers depend on the runtime and how much KV cache the concurrent sequences need.

The limit is memory, not compute. Each concurrent sequence needs its own KV cache — so on the 8 GB machine with 1.7 GB of headroom, four concurrent 8k-token sub-agents want 4.8 GB and you cannot have them. Batching is a big-machine luxury. On the 64 GB machine it is close to free capacity you are currently not using.

Speculative decoding

A small draft model proposes the next several tokens. The large model then verifies all of them in a single forward pass — checking N positions at once, which is compute-bound work, not bandwidth-bound. Accepted tokens are kept; the first rejection resets to that point.

1 weight read → k accepted tokens k depends on how often the draft model guesses right

The output is identical to what the large model would have produced alone — verification enforces that. This is not an approximation; it is the same distribution, arrived at faster.

ConditionEffect
Draft model agrees often (boilerplate, code, structured output)Large speedup — up to ~2× measured
Draft model disagrees often (novel reasoning)Little gain; wasted verification work
Memory-bandwidth-starved machineBigger gain — more idle compute to reclaim
Draft model too largeNet loss — drafting costs more than it saves
The ~2× figure is EAGLE3 on Llama 3.1 8B, measured by LMSYS on DGX Spark.

MTP: the draft model shipped in the box

You have already seen this without knowing it. The unsloth/Qwen3.8-27B-GGUF repository contains an MTP/ directory — multi-token prediction heads, trained alongside the model to predict several tokens ahead. That is a purpose-built draft model, distributed with the weights.

When a release ships MTP files, speculative decoding is not an exotic optimisation you have to assemble — it is a supported configuration, and skipping it leaves a large fraction of the model's speed unclaimed.

And the design consequence for pi: on the big machine, a harness that fans work out to several concurrent sub-agents is not merely tidier than doing it sequentially — it is faster in wall clock by a factor the bandwidth rule alone would tell you is impossible.

Check yourself

Question 1

Batch size 1 to 32 raised decode 18× but left prefill unchanged. Why?

Prefill was already compute-bound. It had no idle compute to reclaim — it was saturating the chip already. Decode was using a fraction of a percent of it, so batching had enormous slack to recover. Batching helps exactly in proportion to how memory-bound you were.
Question 2

You are waiting on a single answer. Does batching help?

No — batching raises aggregate throughput, not per-sequence latency. Batch 32 gave 368 tok/s across 32 sequences, about 11.5 each, versus 20.5 running alone. For a sole user it pays off only with parallel sub-agents.
Question 3

Does speculative decoding change the model's output?

No. The large model verifies every drafted token and rejects any it would not have produced, so the result is drawn from the same distribution as unassisted decoding. The draft model affects only speed, through how often its guesses are accepted.
Question 4

What limits how many sub-agents you can run concurrently?

KV cache memory. Each concurrent sequence needs its own cache, so four 8k-token sub-agents want ~4.8 GB on Qwen3-4B — more than the 8 GB machine's entire headroom. Compute and bandwidth have slack; memory does not. Batching is a big-machine technique.
