Lesson 7 · Local LLM Fluency

Templates and Sampling

The two layers between your JSON and the model's tokens. Both are invisible when they work, and both produce failures that look like the model being stupid.

~18 minutes Prerequisite: Lesson 6 Mission · Glossary

Everything up to here has been physics — bytes, bandwidth, memory. This lesson is the first that is purely about plumbing, and it is where most people lose their first weekend to local models.

The one idea

A model is not just weights. It is weights plus the exact token sequence it was trained to expect. Get that sequence subtly wrong and the model still answers — worse, and with no error anywhere.

Silent degradation is the defining failure mode of local inference. Nothing crashes. The model just seems dumber than the benchmarks promised.

Layer one: the chat template

You send [{role: "user", content: "hi"}]. The model has never seen JSON. Something must convert your messages into the literal string the model was fine-tuned on — special tokens, role markers, whitespace and all. That something is the chat template, a Jinja program shipped inside the GGUF's metadata.

messages (JSON) → chat template → token sequence → model every model family has its own · they are not interchangeable

llama.cpp has two layers of support: a built-in dispatcher that recognises well-known formats, and a full Jinja engine that executes whatever template the model actually ships. The second is what you want, and on the server it is behind a flag:

llama-server -m model.gguf --jinja

Without it you get llama.cpp's best guess at a matching built-in template. Usually close. Occasionally close enough to work and wrong enough to hurt.

Source: llama.cpp chat templates and message parsing.

"It works in LM Studio but not through the API"

This is almost always template-related. The GUI applies the model's own template; your raw /completion call does not. Either use the /v1/chat/completions endpoint and let the server template for you, or reproduce the template exactly. Sending pre-formatted text to a chat endpoint double-applies it — which is its own distinct bug.

Layer two: sampling

The model outputs a probability distribution over every token in its vocabulary. Sampling is how one token is chosen from it — and the parameters are the ones that get copy-pasted between projects with no thought at all.

ParameterDoesIncrease to
temperatureFlattens or sharpens the whole distributionGet more variety; 0 means always take the top token
top_kKeeps only the k most likely tokensAllow a wider field
top_pKeeps the smallest set whose probability sums to pAllow a wider field, adaptively
min_pDrops tokens below a fraction of the top token's probabilityCut harder when the model is confident
repetition_penaltyDown-weights tokens already producedBreak loops — at some cost to correctness

Order matters, and it is not the order they appear in your config file. llama.cpp filters top-k, then top-p, then min-p, then applies temperature to whatever survived. Temperature comes last, so raising it cannot resurrect a token top-p already discarded — a surprisingly common misunderstanding.

The rule for agent work

Play with the preset buttons above and watch the bottom line change. At Qwen3's recommended chat settings the tool call is likely. At temperature 0 it is certain.

For tool calling and structured output, use temperature 0

Sampling diversity is a creative-writing lever. In an agent harness you do not want creative variety in the shape of a function call — you want the same input to produce the same call, every time, so that failures are reproducible.

The default settings shipped with every model are tuned for chat. They are the wrong defaults for a harness, and nothing warns you.

On min-p: it truncates relative to the top token's probability rather than at a fixed cumulative mass, so it adapts to how confident the model is. It was widely promoted, then a 2025 re-analysis found its headline gains sensitive to hyperparameter tuning. Useful, not magic — and irrelevant at temperature 0, where nothing is being sampled anyway.

A diagnostic order

When a local model underperforms, work down this list before concluding the model is bad:

#CheckBecause
1Is it swapping? (Lesson 5)Explains slowness, not wrongness — rule it out first
2Is the right chat template applied?The single most common cause of "this model is dumb"
3Are BOS and stop tokens correct?Causes rambling and subtle degradation
4Is temperature 0 for structured work?Turns intermittent failures into reproducible ones
5Is the quantization above 4 bits? (Lesson 6)Reasoning fails before recall does
6Now consider a different modelBy here you are actually testing the model

Steps 2 through 4 are free and take minutes. Most people skip straight to step 6 and download a bigger model, which costs bandwidth and memory to fix a problem that was never about capability.

Check yourself

Question 1

A model gives coherent but noticeably poor answers and ignores the system prompt. Most likely cause?

Wrong chat template. Coherent-but-degraded plus a disregarded system prompt is the signature: the role markers the model was trained on are not where it expects them, so it treats the system message as ordinary text. Bandwidth affects speed, never quality.
Question 2

In llama.cpp's default sampler chain, when is temperature applied?

Last. The order is top-k, top-p, min-p, then temperature. Because it comes last, temperature reshapes only the surviving candidates — raising it cannot bring back a token that top-p already cut. People frequently expect the opposite.
Question 3

What temperature should an agent harness use for tool calls?

Zero. Variety in the shape of a function call has no upside and makes failures non-reproducible. Vendor settings — Qwen3's 0.7/0.80/20 — are tuned for chat, and inheriting them in a harness is a choice you did not know you were making.
Question 4

A model answers correctly, then keeps writing — inventing the next user turn. What is wrong?

Stop tokens. The model emitted its end-of-turn marker and nobody was listening, so generation continued into what the template told it comes next — another turn. Check the GGUF's EOS metadata against what your client is passing as stop strings.

Next

Temperature 0 makes a tool call likely. It does not make it well-formed — a greedy model can still emit confident, perfectly deterministic malformed JSON. Lesson 8 is about making that structurally impossible rather than merely improbable.
