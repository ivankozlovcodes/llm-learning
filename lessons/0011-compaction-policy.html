Designing a Compaction Policy

The plugin this workspace has been building toward. Every cost model you have learned meets here, and the output is a number you can implement.

~25 minutes Prerequisites: 3, 9 Mission · Glossary

Compaction is the only mechanism that lets an agent session outlive its memory budget. It is also the mechanism that destroys prefix cache reuse. Getting the policy wrong in either direction is expensive, and the right answer is computable rather than a matter of taste.

The one idea

Compaction trades one expensive turn for reclaimed memory. Therefore: compact as late as safety allows, and as deeply as coherence allows.

Frequent shallow compaction is the worst of both worlds — you pay the uncached-prefill penalty often and reclaim little each time.

What compaction actually costs

From Lesson 9, compaction lives in transformContext(), which runs before every LLM call. pi also exposes session_before_compact so an extension can replace the default logic entirely. Whichever you hook, the physics is the same:

CostMagnitudeFrom
Summarisation callOne LLM round tripCan be delegated to a cheaper model
Prefix invalidationNext turn prefills the whole new context uncachedLesson 2 — the dominant cost
Information lossLossy and permanent for the modelpi keeps full history in JSONL; the model does not see it

The middle row is the one people miss. Compaction makes the context shorter, so it feels like it should be faster — but the shortened context is entirely new to the cache, so you prefill all of it. A compaction down to 5,000 tokens still costs a 5,000-token prefill.

The trigger arithmetic

You have everything needed to compute the threshold:

usable context (tokens) = ( budget × threshold − weights ) ÷ KV bytes per token budget from Lesson 5 · KV per token from Lesson 3

On the 8 GB machine with Qwen3-4B Q4_K_M — 4.2 GB budget, 2.50 GB weights, 144 KB per token — at a 90% trigger:

(4.2 × 0.90 − 2.50) GB ÷ 144 KB = ~9,000 tokens compact when the conversation reaches this

Simulate it

Run the same session under each policy. Watch the spikes — every spike is a compaction paying full uncached prefill.

Reading the results

PolicyBehaviourVerdict
Never compactRuns fast, then diesOnly viable if sessions are short and bounded
Frequent and shallow (50%, keep 10)Constant spikes, little reclaimed each timeWorst option. Maximum penalty, minimum benefit
Balanced (75%, keep 6)Periodic spikes, steady memoryReasonable default
Rare and deep (90%, keep 3)Infrequent large spikesUsually optimal. Fewest invalidations

The shape of the answer is the same on both machines, but the stakes differ enormously. On the 8 GB machine compaction fires within a handful of turns and the policy dominates the experience. On the 64 GB machine with an MoE model, many sessions never compact at all — the policy is close to irrelevant, and you should not spend design effort on it.

Why not push the threshold to 99%?

Because the trigger fires between turns and the next turn's tool result is unpredictable. A tool that returns 8,000 tokens when you had 500 of headroom overruns the budget before compaction can run. The gap between your threshold and 100% is insurance against the largest tool result you might plausibly receive — which is another argument for Lesson 10's rule about returning the minimum.

Design decisions, priced

Summarise with a cheaper model

Summarisation is not the task your good model is for. Delegating it to a small fast model removes the round trip from the critical path — and on the 8 GB machine, where you have exactly one model loaded, this argues for doing it on the other machine instead. That is Lesson 12.

Keep the system prompt and tools out of the summary

They are the stable head of the prefix. Compact only the conversation body and the tool definitions stay byte-identical — which means a runtime with block-level prefix caching can still reuse that portion. Rewriting the whole prompt throws away reuse you did not have to lose.

Compact at a turn boundary, never mid-turn

Compacting between a tool call and its result strands the model with a call it cannot see the outcome of. shouldStopAfterTurn and turn_end exist precisely to give you a clean seam.

Preserve structure, not prose

What the model needs from history is which files were touched, what was decided, what failed and why. A flowing narrative summary is longer and less useful than a structured one. Terse and schematic beats readable here — the reader is a machine with a memory budget.

A policy you could implement tomorrow

A correction from Lesson 18

The policy below triggers on memory alone, and that is only half right. There is a second ceiling — attention — past which the model is still answering and is measurably less reliable. On the 8 GB machine memory binds first (~11,800 tokens against ~16,000), so this policy is correct there. On the 64 GB machine it is wrong: memory permits around 328,000 tokens while reliability falls away nearer 32,000, so a memory trigger never fires and quality degrades with no signal at all.

The arithmetic below still stands exactly. It just needs a second trigger beside it — Lesson 18 derives both ceilings and the evidence for the attention one.

The last row is the finding worth carrying. On adequate hardware with the right model, the best compaction policy is one that never runs. Choosing an MoE with few KV heads (Lesson 3) does more for long sessions than any compaction strategy — and it is a decision you make once rather than tuning forever.

Check yourself

Question 1

Compaction shortens the context. Why is the following turn slow?

The prefix was rewritten. Cached keys and values correspond to the old token sequence; the new shortened context is entirely unfamiliar, so all of it is prefilled uncached. Shorter, but paid for in full — which is why compacting often is worse than compacting deeply.
Question 2

Which compaction policy is generally worst?

Frequent and shallow. It pays the invalidation penalty constantly while reclaiming little each time. Never compacting is at least fast until it dies — and for short bounded sessions that is a legitimate choice.
Question 3

Why not set the compaction trigger at 99% of budget?

Tool results are unpredictable. The trigger fires between turns; the next turn might append 8,000 tokens. The gap below 100% is insurance sized against the largest plausible tool result — one more reason to make tools return the minimum.
Question 4

On the 64 GB machine with an MoE model, what is the best compaction policy?

One that never fires. Qwen3-30B-A3B uses 96 KB per token and leaves ~29 GB of headroom — a session would need hundreds of thousands of tokens to trigger. Model choice removed the problem, which beats tuning a policy for it.
