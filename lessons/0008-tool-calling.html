Lesson 8 · Local LLM Fluency

Tool Calling

The capability no amount of bandwidth buys. And the one place where local inference has a genuine advantage over every hosted API.

~20 minutes Prerequisite: Lesson 7 Mission · Glossary

A harness is a loop: the model asks for a tool, you run it, you feed the result back. Every turn depends on the model emitting something your parser can read. Lesson 7 got you a call that is probably well-formed. This lesson is about making malformed output structurally impossible.

The one idea

You do not have to ask a local model for valid JSON. You can make invalid JSON unrepresentable — by filtering the token distribution at every step so only tokens that keep the output grammatically valid survive.

Hosted APIs mostly ask nicely. Running locally, you own the sampler, so you can enforce.

Native is the one you want, and it is a property of the template as much as the weights. A tool-trained model served without a tool-aware template silently degrades to the prompted path — which is exactly the fourth failure mode from Lesson 7, now with visible consequences.

Constrained decoding: the mechanism

At each step the model proposes a distribution over the vocabulary. A grammar knows which tokens could legally come next given what has been emitted so far. Intersect the two, and illegal tokens get probability zero before sampling ever happens.

model distribution ∩ grammar's legal next tokens → sample applied at every step · invalid output cannot be produced

llama.cpp implements this as GBNF — a BNF-style grammar notation — and converts JSON Schema to GBNF automatically via json_schema_to_grammar. So you hand it a schema and it hands the sampler a constraint.

Lazy grammars, and why they matter

A model that must reason before calling a tool cannot be constrained to JSON from the first token — you would forbid the reasoning. Lazy grammars activate only once a trigger appears (the tool-call opening token), leaving prose unconstrained before it. This is what lets constrained decoding coexist with thinking models, and it is why "just force JSON always" is the wrong implementation.

What constraint does and does not fix

FailureGrammar fixes?Why
Prose wrapped around the JSONYesThose tokens become illegal
Markdown fences around the objectYesSame
Missing required fieldYesThe grammar cannot reach a valid end state without it
Wrong type — string where number expectedYesSchema encodes the type
Invented tool nameYes, if enumeratedConstrain the name field to known tools
Plausible but wrong argument valueNoPerfectly valid JSON containing the wrong path
Calling the wrong tool entirelyNoValid call, bad judgement
Not calling a tool when it shouldNoNothing to constrain

The line is sharp and worth internalising. Grammars guarantee syntax. They do not supply judgement. Everything below the line in that table is model capability, and by Lesson 6 it lives on the reasoning curve — the first thing aggressive quantization takes away.

Why small models fail at tools

Pick a tool, extract arguments from context, format them, and stop. That is a multi-step chain, and the two forces you already know both act on it:

ForceFromEffect on tool calling
Quantization damages reasoning firstLesson 6GSM8K −9.3 at 3-bit while recall holds — tool selection degrades before the model looks dumber
Errors compound along a chainLesson 6Four steps at 95% each is 81% end-to-end
Constrained decoding removes syntax errorsThis lessonLeaves only judgement errors — which is the good trade

The practical consequence for an 8 GB machine: a 4B model at Q4 with grammar-constrained output and temperature 0 will produce well-formed calls essentially always, and choose the right tool markedly less often than a larger model would. Design the harness so wrong-tool is cheap to recover from, because it is the failure you cannot engineer away.

What this means for pi

pi's registerTool hands the model a name, a description and a schema. Given the above, three things follow immediately:

DoBecause
Serve with --jinja and a tool-aware templateOtherwise the native tool path is silently unavailable
Pass tools through /v1/chat/completions, not the system promptGets you the template injection and the lazy grammar together
Enumerate tool names in the constraintRemoves hallucinated tools — a whole failure class, free
Verify arguments in the handler, not the promptGrammars cannot check that a path exists; your code can
Throw when a tool fails — do not return the error as contentpi's stated convention: it catches the throw and surfaces it to the model as a failed tool result. Returning an error string as normal content makes failure indistinguishable from success

That last one is the highest-leverage harness decision in this lesson. A malformed call is prevented by a grammar; a wrong call can only be fixed by letting the model see what went wrong and try again. Which costs a turn — and you now know exactly what a turn costs.

Mechanism matters here. pi's agent README is explicit: "Throw an error when a tool fails. Do not return error messages as content." The runtime converts the thrown error into a failed tool result the model can see and react to. Returning an error as content instead makes a failure look like a successful call that returned some text — which the model will cheerfully build on.

Check yourself

Question 1

Grammar-constrained decoding guarantees which of these?

Syntax only. The grammar zeroes out tokens that would break structure, so malformed JSON becomes unrepresentable. It has no opinion about whether the file path is real or the tool was the right one — that is judgement, and judgement is model capability.
Question 2

Why do lazy grammars exist rather than constraining output from the first token?

To permit reasoning first. Constraining to JSON from token one forbids the model from thinking before it acts. Lazy grammars activate on a trigger token, so prose flows freely until the call begins and is rigidly constrained thereafter.
Question 3

A tool-trained model is served without a tool-aware chat template. What happens?

Silent fallback. The tool definitions never reach the model in the form it was trained on, so its native tool tokens are never triggered and it improvises JSON as plain text. Nothing errors — you just get markedly worse reliability and no indication why.
Question 4

Your harness gets a well-formed call to the wrong tool. Best response?

Return an informative error. Tool choice is judgement, which no grammar or sampler setting touches. Feeding the failure back gives the model a turn to correct itself — the only available fix. In pi specifically, throw from the handler; the runtime turns that into a failed tool result. Higher-precision weights help at the margin but do not eliminate it.
