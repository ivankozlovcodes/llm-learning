Anatomy of a Turn

Eight lessons of costs, laid over pi's actual architecture. Every number you have learned lands somewhere specific in this pipeline.

~15 minutes Prerequisites: 2, 8 Mission · Glossary

Lesson 2 modelled a turn abstractly: prefill plus decode. pi has a real pipeline with real extension points, and the costs attach to specific stages. Once you can see which stage owns which cost, plugin design stops being guesswork.

The one idea

pi's context pipeline is
AgentMessage[] → transformContext() → convertToLlm() → Message[] → LLM

transformContext() is where your KV cache lives or dies. It is the hook that prunes and compacts — which means it is the hook that rewrites the prefix. Every other cost in this workspace is downstream of what happens there.

The event timeline

pi emits events you can subscribe to. Mapped against the physics:

EventWhat is happening underneath
agent_startLoop begins
turn_starttransformContext() has run; the prompt is assembled
message_startPrefill is finishing. The gap before this is your TTFT
message_updateDecode, one delta at a time. Rate = the Lesson 1 number
message_endGeneration complete
tool_execution_start / _endYour code. Whatever it returns becomes next turn's prefill
turn_endshouldStopAfterTurn decides whether to loop

The gap between turn_start and message_start is prefill. If you want to know whether your cache reuse is working, that interval is the measurement — no profiler needed. Cached, it should be roughly constant per turn. Uncached, it grows every turn, and you are watching Lesson 2's quadratic curve in real time.

The four hooks, priced

HookFiresWhat it costs you
transformContextBefore every LLM callEverything. Touch the prefix and the next turn pays full uncached prefill
beforeToolCallBefore execution; can { block: true }Nearly free — and it can save a whole turn
afterToolCallAfter execution; can override the resultFree in compute; costs context if it enlarges the result
shouldStopAfterTurnAfter each turnFree. Stopping early saves an entire prefill+decode cycle
The asymmetry worth exploiting

beforeToolCall is the cheapest place in the whole loop to catch a mistake. Blocking a bad call there costs microseconds. Letting it execute, fail, and be corrected by the model costs a full turn — on the 8 GB machine, about 70 seconds. Validation you can express in code should never be delegated to the model.

Tool results are next turn's prefill

This is the fact that reframes tool design. Whatever execute() returns is appended to the conversation, so it is prefilled on every subsequent turn — and with prefix caching, it is the bulk of what you pay for on the turn it arrives.

Tool returnsTokensPrefill on M1 8 GB (~40 t/s)Then, every later turn

A tool that returns too much does not just cost one slow turn — it permanently occupies KV cache for the rest of the session. On a machine with 1.7 GB of cache headroom, one careless cat ends the conversation.

Parallel tools are batching

pi's executionMode defaults to "parallel": preflight sequentially, then execute concurrently. For your own code that is ordinary concurrency. But if a tool is itself an LLM call — a sub-agent — then several in flight at once is exactly the batching case deferred back in Lesson 2, where the Spark went from 20.5 to 368 tok/s of decode throughput.

On a bandwidth-bound machine, running four sub-agents concurrently costs far less than four times one. Lesson 13 does that arithmetic properly.

Check yourself

Question 1

Which pi hook determines whether prefix cache reuse survives?

transformContext. It runs before every LLM call and is where pruning and compaction happen. Any edit to an earlier message changes the prefix, so the cached keys and values no longer correspond to it and the next turn re-prefills from scratch.
Question 2

You want to measure whether cache reuse is working. What do you time?

turn_start → message_start. That interval is prefill. Roughly constant per turn means the cache is being reused; growing every turn means it is not, and you are watching a quadratic session unfold.
Question 3

A tool returns an entire 600-line file. What is the lasting cost?

Permanent cache occupancy. One expensive prefill, then ~8,000 tokens sit in the KV cache for the rest of the session — about 1.1 GB on Qwen3-4B. Caching makes it free in time and permanently expensive in memory, which on 8 GB is the binding constraint.
Question 4

You can validate a tool argument in code. Where should that check live?

beforeToolCall, blocking. It costs microseconds. Letting the call run, fail, and be corrected by the model costs a full prefill-plus-decode cycle. Schemas catch shape but cannot check that a path exists; prompt instructions are advisory and degrade with quantization.
