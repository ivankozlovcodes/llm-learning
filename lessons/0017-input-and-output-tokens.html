Lesson 17 · Local LLM Fluency

Input and Output Tokens

Every cost in this workspace is quoted per token. This is the lesson about the token itself — how one gets counted, why the two directions cost such different amounts, and why your agent produces so few of the expensive kind.

~20 minutes Prerequisites: Lesson 1, Lesson 2 Mission · Glossary · Cheat sheet
The one idea

An output token costs one full pass over the weights. An input token costs a fraction of one, because prefill reads the weights once and applies them to the whole prompt at once. On your M1 that is a measured 8.3× gap.

And the moment an output token is produced it becomes an input token — re-read on every subsequent turn, for the rest of the session.

What a token actually is

A token is an entry in a fixed vocabulary that the tokenizer built by merging frequent character pairs — byte-pair encoding. Qwen3's vocabulary holds 151,669 of them. Common English words are single tokens; rare strings get chopped into pieces.

The folk rule is "about four characters per token". It is true for English prose and badly wrong for the things an agent harness actually moves around. Every figure below was measured by running the text through Qwen/Qwen3-1.7B's tokenizer:

The finding worth keeping

Qwen3 tokenizes every digit separately. 1720574976 is ten tokens. 68.25 is five. A UUID is one token per character.

So a tool that returns numeric tables, hashes, timestamps or aligned columns costs three to five times the tokens per character that prose does. This is the hidden half of Lesson 10's token bill: it is not only how much your tool returns, it is what kind of characters they are.

Why output costs more

This is Lesson 1 and Lesson 2 seen from the token's point of view.

prefill — one input token weights read ÷ N prompt tokens → a fraction of a pass, compute-bound

decode — one output token one full pass over every active weight → bandwidth-bound

Prefill reads each weight once and multiplies it against the entire prompt, so the arithmetic intensity is high and the chip's compute is the limit. Decode reads every weight to produce a single token, so intensity is about 2 FLOPs per byte and bandwidth is the limit. Same weights, same machine, two completely different regimes — which is exactly the roofline argument from Lesson 4.

The gap is measurable. From the community llama-bench table, llama 7B Q4_0 on Metal:

The ratio is a property of the machine, not the model. M1 and M1 Max differ by 4.5× in absolute speed and by almost nothing in the ratio — both are Apple chips with a similar compute-to-bandwidth balance. Change that balance and the ratio moves violently: on the DGX Spark, Llama-70B FP8 runs at 803 tok/s of prefill against 2.7 tok/s of decode, a ratio near 300. A machine's prefill-to-decode ratio is its ridge point from Lesson 4, wearing different clothes. Spark figures from the LMSYS DGX Spark review; different model and precision, so read the ratio, not the absolute numbers.

The market prices the same physics

You are running locally, so nobody bills you. But hosted pricing is a useful independent check on whether the asymmetry is real, because providers have every incentive to price it accurately:

ModelInput /MTokOutput /MTokCached inputOutput ÷ cached
Opus 5$5$25$0.5050×

Haiku 4.5$1$5$0.1050×
From claude.com/pricing. The 5× output multiplier and the 10% cache-read rate hold across every model in the list.

Output is priced at exactly 5× input, and a cache hit costs 10% of input — so a cached input token is 50× cheaper than an output token. Your local machine's numbers differ (8.3× rather than 5×, and a cache hit is free rather than 10%), but the shape is identical, and it points at the same design conclusion: protect the cache, and be careful what you generate.

Why output is usually so much smaller

Now the part that surprises people. Output tokens are the expensive ones, and an agent harness produces almost none of them. Measured, on a modest seven-tool harness:

static prefix, before you type anything · 1,706 tokens
one assistant tool call · 31 tokens
55 input tokens for every output token — on turn one, with no history at all

Three things drive it, and they compound:

CauseEffect
Output stops; input accumulatesThe model emits an end-of-turn token after a short call. The input is everything ever said, plus every tool result.
Input is re-sent every turnTurn 20 re-reads all nineteen previous turns. Output is produced once.
Tool results dwarf tool callsA 31-token call can return 8,572 tokens of file. You spend a little output to buy a lot of input.
The ratchet

Every output token is paid for twice: once at the decode price to produce it, and then on every later turn at the prefill price to re-read it. It never leaves. It is only ever removed by compaction (Lesson 11), which costs an uncached turn to perform.

This is why Lesson 9's "tool results are next turn's prefill" is the most load-bearing sentence in this workspace.

Price it yourself

Predict first

A pi tool of yours runs git log --oneline and returns the raw output — 2,012 characters of short hashes and subject lines. Two questions before you look. Roughly how many tokens? And which half of that text is doing the damage?

678 tokens, measured — 2.97 chars/token. The four-chars rule predicts 503, so it is 35% low. Not catastrophic, and that is the boring half of the answer.

The interesting half is the split. The seven-character hashes are 439 characters — 22% of the text — and 401 tokens, 59% of the bill, at 1.09 chars/token. The subject lines are the other 78% of the characters and only 41% of the tokens, at 4.47. A fifth of the output is costing you three-fifths of the tokens.

So the fix is not "return less". It is "return --format=%s" — drop the hashes and you shed 59% of the token cost while keeping 78% of the text and almost all of the meaning. On the M1, 678 tokens is 5.7 s of prefill on arrival, 98 MB of KV cache held for the session, and about 1.9 minutes of repeated prefill across twenty uncached turns.

Reasoning tokens invert everything

A thinking block is output. It is generated one token at a time, at decode speed, at the expensive end of the asymmetry — and on an 8 GB M1 that is around 14 tokens per second.

2,000 thinking tokens ÷ 14 tok/s = ~2.4 minutes per turn, before the model says anything you can read

A reasoning model turns the agent's normally-favourable token shape upside down: the one workload where output volume becomes the dominant cost. On the 64 GB machine at ~100 tok/s it is twenty seconds and probably worth it. On the travel laptop it usually is not — which is a routing decision (Lesson 12), and a reason to check whether your model lets you disable thinking per-request.

Check yourself

Question 1

Why does one output token cost more than one input token?

Each output token needs a full pass over the weights. Prefill amortises one weight read across the whole prompt; decode cannot, because token n+1 depends on token n. Pricing reflects that fact rather than causing it.
Question 2

Which tool output costs the most tokens per character?

Commit hashes. Measured at 1.07 chars/token against prose's 4.95 — roughly 4.6× worse. Digits and hex tokenize close to one token per character, so hashes, UUIDs, timestamps and numeric tables are the most expensive text an agent can move.
Question 3

Your harness sends 1,706 input tokens and gets 31 back. Which dominates the wait?

Input, on an uncached turn. 1,706 ÷ 118 = 14.5 s of prefill against 31 ÷ 14.15 = 2.2 s of decode. Decode is 8.3× more expensive per token, but there are 55× more input tokens, so input wins by about 6.5×. On a cache hit the prefill approaches zero and decode becomes the whole wait — which is why cache reuse changes the felt character of a session.
Question 4

What happens to an output token once the turn ends?

It becomes an input token, permanently. Paid once at the decode price, then re-read at the prefill price on every subsequent turn until compaction removes it. Cheap on a cache hit, expensive on a miss, and it occupies KV cache the whole time either way.

Addendum · the 48 GB M4 Added 2026-09-05 — the lesson above stands as written; this is what a third machine changes.

The 8.3× prefill-to-decode ratio measured here is a property of the M1's compute-to-bandwidth balance, not a universal constant — the sidenote above says so, and a third machine is the demonstration. The token meter now offers M4 Pro and M4 Max rows; switch between them and watch both the absolute rates and the ratio move.

Apple sells 48 GB on both chips, and they differ by exactly 2× in the specification that sets decode speed. Check which one you have before predicting anything — sysctl -n machdep.cpu.brand_string, then the GPU core count. A 40-core M4 Max is the fastest machine in this workspace, home included.

What does not move: every chars-per-token figure in this lesson. Tokenization is a property of the tokenizer, so hashes still cost 1.07 chars/token on all three machines, and the ratchet — output becoming input forever — is unchanged. More bandwidth makes the bill arrive faster, not smaller. See Three Machines.
