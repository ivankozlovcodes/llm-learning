Reading a Model Card

A repeatable procedure for deciding whether a model will run, how fast, and whether the claims are true — using only what the publisher already gave you.

~12 minutes Prerequisites: 3, 6 Mission · Glossary

You have watched this done several times now. This lesson turns it into a checklist you can run in about two minutes on any model, and it deliberately never trusts the README.

The one idea

Everything you need is in two places the publisher cannot fudge: the config.json and the file sizes. The README is marketing; those two are measurements.

The six-step pass

1. Parameter count — from the BF16 files, not the name

Sum the unquantized files and divide by 2 bytes per parameter. Qwen3.8-27B's BF16 shards total 54.7 GB, so it is 27.3B parameters. Names round, and some "9B" models are 9.2B in ways that matter at the memory boundary.

2. Effective bits per weight — from the file you will actually download

file bytes × 8 ÷ parameters = real bpw

This is the step that told you UD-IQ1_S is 1.81 bits, not 1. Do it every time. Quant labels are family names, not measurements.

3. Active vs total parameters — the MoE question

num_experts and num_experts_per_tok in config.json. Total sets whether it loads; active sets how fast it decodes (Lesson 1). An A3B suffix names the active count directly. This single distinction is the largest source of wrong speed expectations in local LLM discussion.

4. KV cache geometry — the number nobody quotes

2 × layers × kv_heads × head_dim × 2 bytes = bytes per token

Read num_hidden_layers, num_key_value_heads, head_dim. This varies by an order of magnitude between models of similar size and it is never in the README. Ornith-1.5-35B-A3B has 2 KV heads and needs 80 KB per token; Qwen3 32B has 8 and needs 256 KB. That is a bigger practical difference than most benchmark gaps.

5. Context: advertised vs affordable

max_position_embeddings is what the model was trained for. (your budget − weights) ÷ KV bytes per token is what you can hold. Lesson 5 found a 26× gap on the 8 GB machine. Always compute the second number; never quote the first.

6. Licence — from the API, not the README

The cardData.license field on the Hugging Face API is the machine-readable answer. MIT and Apache-2.0 are unencumbered; several major releases ship under bespoke conditional licences that restrict commercial use or scale.

The benchmark that matters

None of the published numbers measure your workload. If you are building an agent harness, the only evaluation that counts is: does this model emit correct tool calls, on your schemas, in your context, at your quantization? Twenty saved transcripts from your own harness outrank every leaderboard — and unlike a leaderboard, they cannot be gamed by the publisher.

Check yourself

Question 1

Where do you get a model's true parameter count?

BF16 total ÷ 2 bytes. Unquantized weights are exactly two bytes per parameter, so the file size is a direct measurement. Names round — "27B" was really 27.3B — and a quantized file cannot give you the count without already knowing the bits per weight.
Question 2

Which config field most affects how much context you can afford?

KV heads. They multiply directly into bytes-per-token, and they vary hugely — 2 on Ornith-35B-A3B versus 8 on Qwen3 32B, a 4× difference in cache cost. Max position embeddings tells you what the model was trained for, which is not what you can hold.
Question 3

A README says "runs on 8 GB". What is it most likely omitting?

KV cache and OS overhead. "Runs on 8 GB" almost always means the weights file is under 8 GB. Add an agent-scale cache and 3 GB of macOS and the real requirement is often double. This is exactly how a 6.19 GB model becomes unrunnable on an 8 GB machine.
Question 4

For choosing a model for your harness, which evidence ranks highest?

Your own transcripts. They measure the thing you actually need — correct tool calls on your schemas at your quantization — and cannot be gamed. Independent leaderboards come second; publisher tables are the weakest evidence and the most prominently displayed.
