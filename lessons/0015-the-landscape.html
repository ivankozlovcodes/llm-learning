The Landscape

Who ships what, as of September 2026 — and the structural shifts that will still be true when every name here is stale.

~20 minutes Prerequisite: Lesson 14 Mission · Resources
Read this first

Specific model names age in weeks. Architecture facts below — parameter counts, KV geometry, licences, file sizes — were read directly from Hugging Face config.json and the file API, and are reliable. Benchmark claims come from secondary aggregators and vendor announcements; treat them as directional, and apply Lesson 14's scepticism. The patterns in the last section are the part worth memorising.

Four structural shifts

1. Sparse MoE has won at the local tier

The best models you can run at home now activate a small fraction of their parameters. Ornith-1.5 is 35B total and ~3B active; Qwen3.8-Flash-Next is 125B with 6B active. This is the direct consequence of Lesson 1: capacity is cheap in RAM, speed is expensive in bandwidth, so architectures moved to buy capability with parameters you do not have to read.

2. KV heads collapsed

Grouped-query attention went from 8 KV heads to 2 in the current generation, with head-dim rising to 256 to compensate. Ornith-35B-A3B needs 80 KB per token; Llama 3.3 70B needs 320 KB. Long context stopped being a memory problem largely because of this, and it is invisible on every spec sheet.

3. Draft models ship with the weights

Both current Qwen releases include MTP/ directories — multi-token prediction heads for speculative decoding (Lesson 13). Qwen3.8-Flash-Next dedicates a 4B module to it. Inference acceleration has moved from a technique you assemble to a component you are handed.

4. Multimodal is the default, and it costs you

Nearly every current release ships an mmproj file — a vision projector, typically 0.85–0.93 GB. If you are building a text coding agent, that is memory you do not load. Worth knowing it is optional; several people budget for it by accident.

A correction to Lesson 3

Lesson 3 named Qwen3-30B-A3B "the answer" for the 64 GB machine. On the numbers, Ornith-1.5-35B-A3B is strictly better: comparable active parameters, a smaller KV cache (80 KB vs 96), MIT rather than Apache, and materially stronger reported agentic-coding results. At 21.71 GB of weights plus 10.7 GB for a full 128k context, it fits in ~48 GB with room to spare and should decode at roughly 100 tok/s.

Lesson 3's reasoning still holds exactly — small active count, few KV heads. A better model arrived that satisfies the same criteria harder. That is what the criteria are for.

Check yourself

Question 1

Why did local-tier models converge on sparse MoE architectures?

Capacity is cheaper than bandwidth. RAM is comparatively easy to add; memory bandwidth is not. MoE buys capability with parameters that are stored but not read per token, which is precisely the resource local machines have spare. Lesson 1, expressed as an architectural trend.
Question 2

Current models dropped from 8 KV heads to 2. What did that buy?

Cheaper long context. KV heads multiply directly into cache bytes per token — 80 KB on Ornith-35B-A3B versus 320 KB on Llama 3.3 70B. Decode speed comes from active parameter count, and weight file size is unaffected.
Question 3

A repo contains an MTP/ directory. What are you being offered?

Speculative decoding draft heads. Multi-token prediction modules trained alongside the model to guess several tokens ahead, which the main model then verifies in one pass. Free speed — but only if you configure it. A vision projector is mmproj.
Question 4

When should you switch the model your harness uses?

When your criteria are beaten. Small active count, few KV heads, ≥4 bits, reliable tool calls on your schemas, workable licence. Ornith displaced Qwen3-30B-A3B because it beat those, not because it was newer — and a release that beats none of them is not an upgrade regardless of its benchmark table.
