Fine-Tuning & Merging

Memory arithmetic, the mlx-lm flag map, and the merge methods worth knowing by name. Sized against an 8 GB Mac. Print it.

Established in Lesson 16 Pairs with Napkin Math · Glossary

Decide first: should you?

No — valid JSON, a persona, knowledge of your files, stray tokens before a call. Grammar, system prompt, and retrieval do these better and for free.
Yes — which tool to call, when to stop, matching a bigger model on one narrow job you can demonstrate a thousand times.
Rule — build the held-out eval set before training. Without it you cannot tell whether the fine-tune helped, and you cannot make a soup.

The four terms

peak training memory base weights + gradients + optimizer state + activations
TermScales withSizeLever
Base weightstotal params × bpwparams × 0.563 at 4-bitQuantize the base (QLoRA)
Gradientstrainable params2 B/param (bf16)LoRA
Optimizer statetrainable params4 B/param (AdamW m + v)LoRA
Activationsbatch × seq × layers × hidden≈ seq × h × 34 B per trained layerBatch, seq length, --grad-checkpoint

Whole training state (params + grads + both moments) is 8 bytes per trainable parameter in MLX, 16 in PyTorch mixed precision. The activation figure is an order-of-magnitude estimate, good to about ±2×.

Constants derived from measured mlx-community safetensors sizes; they reproduce Qwen3-0.6B (0.335 GB) and Qwen3-4B (2.263 GB) exactly. Same effective bpw as GGUF's F16 / Q8_0 / Q4_K_M — see Napkin Math.

LoRA parameter count

per adapted matrix rank × (fan_in + fan_out) × number of tuned layers

Worked, Qwen3-1.7B at mlx-lm defaults (rank 8, q_proj + v_proj, 16 layers, hidden 2048, 16 query heads, 8 KV heads):

q_proj 8 × (2048 + 2048) = 32,768
v_proj 8 × (2048 + 1024) = 24,576
(32,768 + 24,576) × 16 = 917,504 → 0.053% of 1.72B → 7 MB of state

The commands

pip install "mlx-lm[train]"

mlx_lm.lora --model mlx-community/Qwen3-1.7B-4bit --train --data ./data \
  --batch-size 1 --num-layers 8 --max-seq-length 1024 --mask-prompt \
  --iters 300 --adapter-path ./adapters-a

mlx_lm.lora --model … --adapter-path ./adapters-a --data ./data --test
mlx_lm.generate --model … --adapter-path ./adapters-a --prompt "…"
mlx_lm.fuse --model … --adapter-path ./adapters-a --save-path ./fused-a

mergekit-yaml merge.yml ./soup --lazy-unpickle

Souping

Precondition — every ingredient fine-tuned from the same base checkpoint. Fine-tunes of one checkpoint lie in a single low-error basin; independently pretrained models do not, and average to noise.
Greedy > uniform — sort runs by held-out score, best first; add each only if the soup's score does not fall. Can be no worse than the best single run.
Cost — zero at inference. One model, original size. This is why soup is available on 4.2 GB and ensembling is not.
Trap — averaging LoRA A and B separately gives ¼(B₁A₁ + B₁A₂ + B₂A₁ + B₂A₂): half signal, half noise. Concatenate the factors (PEFT combination_type="cat", rank doubles), use svd, or fuse each adapter into a full model first and average those.
